# 当前功能盘点与能力边界

> 验收时间：2026-07-31。
> 验收环境：`10.1.18.100` 正式 Compose 栈 + 宿主机 systemd Agent。
> 本文只写已经通过代码、容器、数据库或浏览器验证的事实。

## 一、产品结论

当前版本已经形成可运行的单机态势感知候选产品：本机镜像流量和主机 Agent 数据能进入统一检测引擎，XDR 能关联成 ATT&CK 攻击链并生成可处置 Incident，规则能在线更新、签名、热加载和回滚，Web 控制台及全球态势大屏可用。

这不等于已经完成所有政企现场认证。独立 CentOS 7/Linux 3.10 主机 72 小时运行、真实业务应用 RASP 兼容矩阵、ARM 实机和检测效果指标仍需要目标环境证据。

## 三、为什么保留 9 个容器

正式默认栈只运行以下 9 个容器，没有两个 RC 栈并行：

1. `ly-vis`：HTTPS 和 Web 控制台。
2. `ly-server`：业务 API、认证、XDR 和 Incident。
3. `agent-center`：Agent 注册、上线、控制和任务管理。
4. `ly-local-mirror`：PF_RING 本机镜像采集。
5. `ly-suricata-sensor`：流量 IDS 检测。
6. `ly-security-engine`：统一消费 DPI、Runtime、日志、RASP 和 YARA 结果。
7. `PostgreSQL`：账号、配置、事件、Incident 和审计等事务数据。
8. `ClickHouse`：长期、高容量全量会话和分析数据。
9. `Redis`：实时事件总线和短期缓冲，不是正式数据仓库。

这些职责不建议继续硬合并。合并会让抓包、检测、业务 API 或数据库故障互相拖垮，升级和定位也更困难。`ly-engine-lab`、容器 Agent 和 legacy DPI 已退出默认生产运行面，只保留 QA/兼容 profile。

## 四、数据职责

- PostgreSQL 与 ClickHouse 不冲突：前者负责需要一致性和状态变更的数据，后者负责大规模追加写、长期留存和追溯查询。
- Redis 只负责传递与短时缓冲。正式事件、Incident、规则状态和会话不能只存在 Redis。
- 当前六条主要 Redis 消费链路 pending 和 lag 均为 0；Agent 服务切换时产生的加密 spool 已全部重放。
- 安全引擎健康消息已经从业务 runtime 流分离到 `control:health`，开发期死信已清零。

## 五、已明确隔离的兼容组件

- `container-agent`：仅用于自动化和兼容测试，真实场景使用无容器 systemd Agent。
- `legacy-dpi`：旧 `flows:raw` 检测实现，仅用于迁移对账，不与统一引擎长期并行。
- `ly-engine-lab`：历史外部引擎试验壳，不属于正式默认栈；现有生产能力不依赖它。
- Java RASP：仍是实验能力；当前生产验收范围是 Python RASP。

## 六、不能扩大承诺的边界

1. 当前是单机部署，不承诺多节点高可用或跨站容灾。
2. amd64 和 arm64 Agent 均已构建，但 arm64 尚未在真实 ARM 主机长期运行。
3. Agent 已在当前 Ubuntu 宿主机无容器运行，尚缺独立 CentOS 7/Linux 3.10 目标机 72 小时认证。
4. 大屏会绘制全部国家边界；当前环境没有真实公网攻击源，所以动态攻击路线为 0，不使用假攻击数据填充。
5. XDR 当前提供人工处置建议，不自动隔离主机或封禁网络；自动执行需要审批、回滚和失联保护。
6. 规则数量和链路可用不代表检测质量已经商业化量化，仍缺持续 corpus、误报率、召回率和性能基线。
7. RASP protect 模式已打通，但在没有真实业务兼容矩阵前，不应对所有语言和框架承诺生产阻断。

# 后续工作计划

> 本计划替代散落在历史版本对比、TODO 编号和验收记录中的旧计划。
> 产品目标沿用原设计：证据优先、低噪声、状态可持久、规则可运营、离线可交付；政企现场以无容器 Linux 3.10 Agent 为第一优先级。
> 计划基线：`takeover/20260730` / `c93d960`。

## 目标状态

平台服务端以单机离线栈形成稳定控制面；业务主机只安装静态 Agent，只需访问平台 HTTPS。采集数据经过可恢复传输进入统一安全引擎，事件和 Incident 具有持久化权威，规则与版本可审计回滚。实验组件不混入生产承诺，所有“完成”都有目标环境证据。

## 执行原则

1. 先打通真实远端 Agent，再扩展页面和检测类型。
2. Redis 只做事件总线，不做外部 Agent 接入面或正式数据权威。
3. 新能力先定义契约、失败策略和持久化，再实现 UI。
4. legacy/experimental/QA 必须 profile 隔离；没有迁移输入时不进入生产镜像启动面。
5. 每阶段必须满足退出标准，未满足不得以“代码已存在”标记完成。

## P0：基线收敛与文档契约一致性

目标：形成唯一可信的功能清单、计划和机器契约。

- 归档历史版本对比，建立文档索引、功能盘点和本计划。
- 重新生成 route API contract，使 Agent snapshot 的凭据类别与代码一致。
- 删除或隔离不再由 router 使用的旧导航配置，认证后未知路由返回真实 404。
- 修复 Suricata golden replay 漂移，确保 Agent 全量测试无已知失败。
- CI 增加文档链接、路由契约和功能盘点变更检查。

退出标准：工作树干净；机器契约生成测试通过；前后端、Agent 和 smoke 基线全绿；不存在第二份活动计划。

## P1：政企无容器 Agent 生产化

目标：CentOS 7/Linux 3.10 业务主机无需 Docker、无需 Redis 访问即可稳定接入。

- 将 traffic、runtime、log-audit、RASP health、任务和状态统一到 Agent 凭据保护的 HTTPS 摄取面。
- 删除外部 Agent 对 Redis 地址、ACL 和端口可达性的生产依赖；Redis 仅留在平台内网。
- 提供独立的宿主机 Agent 离线包：静态二进制、systemd unit、配置签名、CA 信任、安装/升级/回滚/卸载脚本。
- 在控制台实现 enrollment token 的签发、吊销、TTL、一次性消费和审计工作流，禁止长期 token。
- 建立 CentOS 7/Linux 3.10、较新 Linux、无互联网、服务端短时中断和磁盘压力矩阵。
- 明确 auditd fallback、AF_PACKET 权限、受限 BPF、spool 满载和降级状态的可观测输出。

退出标准：隔离远端 CentOS 7 只开放 443，连续运行至少 72 小时；注册、心跳、资产、流量、runtime/log、断线补传和升级回滚全部有自动证据；平台不暴露 Redis。

## P2：统一检测引擎和 legacy 退场

目标：所有生产检测进入统一遥测契约和规则生命周期，legacy DPI 只保留可删除的迁移闸门。

- 固定 traffic/runtime/RASP/log-audit envelope、幂等 UID、来源身份和时间语义。
- 建立真实流量与攻击行为 corpus，按规则版本统计 recall、FPR、丢弃、采样、延迟和重复率。
- 收敛 Agent 侧端口扫描与服务端规则的职责，避免同一行为重复告警。
- 完成 legacy DPI 与统一引擎结果对账，定义停止条件、最后支持版本和删除清单。
- 对 Suricata/Wazuh/YARA/RASP 外部输出实施健康、超时、隔离和 provenance 准入。

退出标准：默认栈不读取 legacy `flows:raw` 检测路径；相同 corpus 结果可重复；规则升级失败可自动回滚；噪声和质量指标进入控制台与发布证据。

## P3：数据权威与可靠性闭环

目标：重启、短时依赖故障和迁移过程不造成不可解释状态。

- 明确 PostgreSQL canonical tables、ClickHouse analytics reader 和 Redis transient streams 的权威关系。
- 用正式规模数据执行 ClickHouse 双写、reconcile、backpressure、read-switch、observe 和 rollback 演练。
- 将镜像接口、规则订阅、RASP 开关、系统时间等 runtime-only 变更改为持久化、版本化和可审计配置。
- 统一 producer/consumer spool、ACK、reclaim、dead-letter、容量和年龄告警。
- 增加备份恢复、磁盘耗尽、Redis 重启、数据库延迟和服务重启的故障注入验收。

退出标准：每个可变状态都有权威存储和重启恢复测试；ClickHouse 只在对账门槛通过后切读；故障期间数据去向和恢复结果可审计。

## P4：XDR 运营与人工处置闭环

目标：从“关联展示”推进到可分派、可复盘、可度量的安全运营工作台。

- 完善 Incident 分派、状态、评论、证据、抑制、合并、SLA 和不可变审计。
- 将 XDR active 与 shadow replay 的差异、误报反馈和规则版本关联到运营流程。
- 前端落实 admin/analyst/viewer 权限差异，不再让所有业务页仅 admin 可用。
- 整理 21 个当前业务路由，合并 6 个重复页面，删除旧导航和未挂载页面声明。
- 响应候选继续保持只读，直到产品负责人确定执行边界。

退出标准：分析员可以在不具备管理员权限的情况下完成查看、分派、研判和关闭；所有状态变化重启后保持；审计可回放。

## P5：响应、RASP 与平台规模的决策闸门

本阶段不默认启动，必须先完成产品决策：

- 响应模式选择“只给建议”“人工确认后执行”或“策略自动执行”。若允许执行，必须先实现审批、目标绑定、幂等、超时、回滚、审计和失联保护。
- RASP 确定只做 monitor，还是允许特定语言和规则进入 block；Java 在没有真实应用兼容矩阵前保持 experimental。
- 部署范围确定继续单机，还是进入 HA/容灾；若进入 HA，需重新设计数据库、Redis、ClickHouse、证书、负载均衡和升级协调。
- arm64 是否成为正式交付架构；若是，必须建立与 amd64 对等的镜像、Agent 和目标机验收。

退出标准由选定方向另立验收契约，未决策项不得出现在生产宣传中。

## P6：离线交付与持续验收

目标：每个受支持组合都能从签名产物安装、升级和回滚，而不是依赖开发机状态。

- 服务端离线包和宿主机 Agent 包分别签名、分别安装，信任根不放回产物内部。
- 固定 Go/Node/基础镜像/第三方引擎来源，保留 SBOM、漏洞记录、例外和到期复审。
- 建立 fresh install、upgrade、rollback、credential rotation、证书替换和灾难恢复自动验收。
- 发布说明从功能盘点自动引用能力状态，禁止把 experimental/QA 生成成生产能力。

退出标准：候选包在干净目标机完成全链路验收；失败升级恢复旧栈；凭据、私钥和 token 不进入日志、文档和发布包。

## 当前决策假设

在产品负责人确认前，本计划采用以下保守默认值：

1. 响应候选只读，不执行自动阻断。
2. Python/Java RASP 均以 monitor 为生产上限，Java 继续 experimental。
3. 正式交付以单机 amd64 服务端和 Linux amd64 Agent 为基线，不承诺 HA 或 arm64 parity。

这些假设只影响 P5，P0-P4 和 P6 可以继续推进。

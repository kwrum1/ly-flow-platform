# 后续工作计划

> 基线：2026-07-31 容器与宿主机 Agent 验收结果。
> 本计划只保留尚未取得充分证据的工作；已经完成的修复不再重复列为待办。

## 目标

把当前单机候选版本推进到可在政企现场复制交付的成熟版本。判定标准不是“代码存在”，而是目标系统连续运行、故障可恢复、检测效果可量化、升级可回滚。

## P1：现场 Agent 认证

目标：证明 Agent 在用户真实旧系统上不依赖 Docker、Redis 或新 glibc。

- 在独立 CentOS 7/Linux 3.10 主机仅开放平台 HTTPS，连续运行至少 72 小时。
- 验证注册、心跳、资产、AF_PACKET、auditd fallback、日志、YARA、RASP、断线 spool 和重放。
- 验证安装、升级、失败回滚、卸载、令牌过期、凭据轮换和磁盘压力。
- 在真实 ARM64 主机重复同一矩阵；amd64 与 arm64 采用同一发布门槛。

退出标准：两种架构均无崩溃、无数据丢失、无外部 Redis 依赖，重启和网络中断可自动恢复。

## P2：检测质量和容量基线

目标：从“能够告警”推进到“知道告警质量”。

- 建立经过标注的流量、日志、Runtime、YARA 和 RASP corpus。
- 每个规则版本统计召回率、误报率、重复率、处理延迟和资源消耗。
- 对 PF_RING 压测不同包长和速率，记录抓包丢包、Suricata 丢包和 ClickHouse 写入延迟。
- 为 Agent 设定小流量 CPU、内存、磁盘和 spool 上限，超限必须可见并降级。
- 将质量门槛加入规则激活和发布流程，不达标自动拒绝或回滚。

退出标准：发布报告能回答“检测了多少、漏了多少、误报多少、最大承载多少”。

## P3：RASP 业务兼容

目标：让 protect 模式在明确范围内可安全承诺。

- 选择正式支持的语言、框架和版本，当前先以 Python 为基线。
- 在真实 Web 应用验证命令执行、文件访问、网络访问和反序列化等检测点。
- 对每条阻断规则验证误伤、超时、fail-open/fail-closed、回滚和审计。
- Java RASP 在完成同等级矩阵前保持 experimental，不进入默认安装。

退出标准：支持矩阵内可开启防护，矩阵外自动保持 monitor 并明确提示。

## P4：安全运营增强

目标：让分析员长期使用，而不只由管理员操作。

- 完成 admin、analyst、viewer 的页面和操作权限差异。
- 增加 Incident 分派、评论、合并、抑制、SLA 和批量操作。
- 对响应建议增加人工审批、目标绑定、幂等、超时、回滚和失联保护，再决定是否开放执行。
- 给大屏接入正式 GeoIP 库更新；没有真实攻击源时继续显示明确空态，不生成假路线。

退出标准：分析员无需管理员权限即可完成研判到关闭，所有操作有不可变审计。

## P5：交付和灾难恢复

目标：候选包能在干净机器重复安装、升级和恢复。

- 生成 amd64/arm64 服务端与 Agent 签名产物、SBOM、漏洞例外和来源清单。
- 执行 fresh install、upgrade、rollback、数据库备份恢复、证书替换和磁盘耗尽演练。
- 正式镜像使用不可变 digest；发布私钥不进入镜像、代码库或日志。
- 若产品需要多节点 HA，另立 PostgreSQL、Redis、ClickHouse、证书和升级协调设计，不把单机栈包装为 HA。

退出标准：在全新目标机完成一键安装与升级，任何失败都能恢复到旧版本和一致数据。

## 产品验收口径

当前版本可作为单机功能候选版本继续试用。完成 P1、P2、P3 和 P5 后，才建议称为面向目标政企环境的成熟正式版本；P4 中自动响应和多角色运营可按商业版本范围分期交付。

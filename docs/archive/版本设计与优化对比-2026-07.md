## 执行摘要

这次版本把平台从“功能集合可运行”推进到“状态、事件、规则和交付均有明确控制面”的生产形态。产品侧的核心变化是持久化 incident 生命周期、canonical event 迁移、XDR active/shadow 重放隔离、签名规则发布、可靠传输和统一 runtime health；访问控制也从路由和 WebSocket 两个入口收紧为认证、principal、Origin、限流和审计共同约束。

交付侧形成了本地 Gitea 驱动的离线流水线：发布镜像使用 digest，外置 Ed25519 trust root 负责验签，安装器在健康检查失败时恢复旧目录和旧栈，runner 固定 Go 1.26.5、Node 22.22.2、libpcap/PyYAML，并复用受控缓存和工作空间。当前 run `32` 成功，release `71` 已指向当前提交，amd64 资产的 API 大小与下载端 HTTP `Content-Length` 一致。

主要采用结论是：当前发布可按 amd64 离线包进行验收；arm64 不能按基线的资产存在推断为当前平权支持。Java RASP 仍为 experimental、monitor-only、非阻塞能力，不应作为生产阻断或生产防护承诺。第三方容器扫描发现已记录为 evidence 而非自动阻断项，这是一项明确的交付风险接受策略。

## 产品设计变化

### 1. Incident 成为持久化生命周期

Incident 只由关联链进入生命周期，不把普通单条事件直接升级为攻击链。当前实现提供 `open`、`triaged`、`processing`、`resolved`、`closed` 等状态、合法迁移和来源约束；每次命令带幂等键与 payload hash，相同请求可安全重放，不同 payload 产生冲突。状态、版本和不可变审计在同一事务内提交，legacy snapshot 经过校验、checksum 和 cutover marker 后原子导入。

这使重启、并发更新和迁移失败都成为可判定的状态问题，而不是依赖进程内记忆。主要参考：[incidentlifecycle/types.go](../../server/incidentlifecycle/types.go)、[transition.go](../../server/incidentlifecycle/transition.go)、[cutover.go](../../server/incidentlifecycle/cutover.go) 及 [incident-lifecycle-evidence.txt](../../scripts/qa/incident-lifecycle-evidence.txt)。

### 2. Canonical event 与迁移阶段化

事件迁移采用 `reader_first -> dual_write -> reconcile -> read_switch -> observe -> retire_legacy`。确定性 event UID、PostgreSQL outbox、checkpoint、reconcile watermark 和 backpressure 共同约束 PostgreSQL/ClickHouse 双写；对账不一致或 ClickHouse 不可用时不得切读。legacy read 观察期和旧 revision 检查使回滚与退役有明确门槛。

参考：[event_migration.go](../../pkg/contracts/event_migration.go)、[storage_migration.go](../../server/analytics/storage_migration.go) 和 [CLICKHOUSE_EVENT_MIGRATION.md](../CLICKHOUSE_EVENT_MIGRATION.md)。这是一套迁移控制设计，不代表所有历史数据已经无条件完成迁移。

### 3. XDR active 与 shadow replay 分权

重放固定区分 `v2-active` 和 `v3-shadow`：active 对 immutable baseline 运行，shadow 用于 recall/FPR 对比和校准。corpus、baseline、workflow、算法 descriptor 与 rule 都有 checksum；shadow 结构上不拥有 promotion、prevention 或商业效果权威，过期 representative review 也会被拒绝。参考：[replay/run.go](../../server/xdr/replay/run.go)、[replay_blockers_test.go](../../server/xdr/replay/replay_blockers_test.go) 和 [detection replay manifest](../../fixtures/detection-replay/v1/manifest.json)。

### 4. 签名规则生命周期

规则从 source pin、URL/大小/digest 校验，进入严格编译和不可变 candidate，再通过签名 manifest 激活；runtime reload 后必须回报健康。激活、reload 或校验失败会恢复 manifest/runtime snapshot 并写入失败或 rollback audit，控制动作受角色约束。规则信任根使用分离的 Ed25519 根材料。

参考：[rulelifecycle/types.go](../../server/rulelifecycle/types.go)、[manager.go](../../server/rulelifecycle/manager.go)、[activation.go](../../server/rulelifecycle/activation.go) 和 [rule-lifecycle-evidence.txt](../../scripts/qa/rule-lifecycle-evidence.txt)。

### 5. 传输可靠性与运行健康

生产者先写入 AES-GCM 加密 WAL，再投递 Redis；消费者在 ACK 前完成 durable accounting/materialization，失败后支持 retry、reclaim、spool 和 dead-letter。spool 具备原子写入、fsync、容量/年龄上限以及 corrupt/stale quarantine。参考：[transportreliability](../../pkg/transportreliability/)、[producer.go](../../pkg/transportreliability/producer.go) 和 [consumer.go](../../pkg/transportreliability/consumer.go)。这些机制降低故障期间的丢失风险，但不能宣称零丢失。

Agent、安全引擎、Python RASP 和实验 Java RASP 共享 `lyflow.control_health.v1` 语义，包含队列、读取、CPU/内存、重启预算、看门狗、fail policy 和 publication retry。完整性失败、授权失败或重启预算耗尽会关闭 prevention；单纯观察链路故障按 fail-open observation 处理。参考：[runtime_health.go](../../security-engine/engine/runtime_health.go)、[agent runtime health](../../agent/cmd/runtime_health.go) 和 [runtime-health-evidence.txt](../../scripts/qa/runtime-health-evidence.txt)。

### 6. WebSocket 与 bootstrap 默认值

WebSocket 升级要求认证 user/agent、principal 绑定和 Origin 检查，并限制连接数、消息和速率；audit 不可用时 fail-closed。整体路由采用 deny-by-default 与角色策略。参考：[websocket.go](../../server/api/websocket/websocket.go)、[websocket_test.go](../../server/api/websocket/websocket_test.go) 和 [route_registry.go](../../server/cmd/route_registry.go)。

Bootstrap secret 使用 32 字节 CSPRNG，数据库只保存 SHA-256 hash，默认 15 分钟 TTL、一次性消费且只允许 loopback；安装器生成初始管理员密码并写入权限为 `0600` 的文件，首次登录必须改密。文档不包含任何凭据。参考：[bootstrap.go](../../server/modules/auth/bootstrap.go)、[bootstrap_handler.go](../../server/modules/auth/bootstrap_handler.go) 和 [README.md](../../README.md)。

### 7. Java RASP 的明确边界

Java RASP 是 monitor-only、allowlist-only、bounded、experimental-only 能力。默认 instrumentation 仅面向 fixture 范围；exporter 使用有界队列和异步 worker，队列满时拒绝并发布健康状态，不阻塞业务调用方。它不进入默认生产防护承诺，也不应作为发布阻断条件。参考：[Java RASP README](../../agent/rasp/java/README.md)、[InstrumentationScope.java](../../agent/rasp/java/src/main/java/com/lyflow/rasp/java/config/InstrumentationScope.java) 和 [java-rasp-experimental-profile_test.sh](../../scripts/qa/java-rasp-experimental-profile_test.sh)。

## 交付与 CI 架构变化

### 离线信任、镜像和回滚

当前离线构建只对 release compose 镜像使用 digest pin，安装器要求包外 `release-root.pem`，先验证签名 manifest、镜像复制/加载和健康状态，再切换服务。升级会把旧目录改为带时间戳的 backup；新栈启动或健康检查失败时停止新栈、恢复旧目录并尝试启动旧栈。参考：[build-offline-release.sh](../../scripts/build-offline-release.sh)、[install-offline.sh](../../scripts/install-offline.sh) 和 [RELEASE_PROVENANCE.md](../RELEASE_PROVENANCE.md)。

外置签名根减少私钥进入工作区的机会，但签名资产、外部密钥、时间戳和实际镜像来源仍是复现边界。因此本版本不宣称完整、无条件的签名产物可复现；使用方仍需保管并独立核验 trust root。

### 本地 Gitea 与生产 runner

工作流从本地 Gitea checkout 并使用离线缓存，runner 使用 digest 固定的 runner 镜像，提供 Go `1.26.5`、Node `22.22.2`、libpcap/PyYAML，并执行 workflow、容器 smoke、安装器和发布来源测试。npm cache、Go module/build cache、Actions cache 与 scanner cache 持久化，workspace 与 Docker 共享以支持离线构建。

该 runner 使用 `network_mode: host`、`/var/run/docker.sock`、host cache/workspace，因此 runner 主机对网络、Docker 和缓存具有权威性；这不是普通无特权 CI 隔离模型，部署方必须把 runner 主机作为受信任交付节点。上述 Gitea runner 与工作流已退出当前发布链路，本段只保留为历史设计记录；当前流程以 [GitHub CI](../GITHUB-CI.md) 为准。

release evidence 阶段会记录镜像扫描和第三方镜像结果；当前第三方镜像 findings 被记录为 `RECORDED`，不再自动阻断发布。容器 smoke 则独立验证 API、前端、依赖服务和 Server 重启。前者是明确的交付风险接受，不是“零漏洞”结论，也不等于容器问题被消除。

## 兼容性与限制

1. **架构**：当前发布自动资产只有 amd64。arm64 需要架构专用 Postgres/Redis/ClickHouse image digest，并提供 ARM64、CGO/libpcap 可用的 Agent binary，或准备 ARM64 CGO 交叉工具链；安装器会拒绝 host/package 架构不匹配。参考：[build-offline-release.sh](../../scripts/build-offline-release.sh) 与 [install-offline.sh](../../scripts/install-offline.sh)。
2. **Java RASP**：experimental、monitor-only、非阻塞、allowlist-only；不提供生产防护或商业效果承诺，不能替代稳定 RASP 方案。
3. **Runner 权限**：host network、Docker socket、host workspace/cache 使 runner 主机拥有交付权威，需专门隔离、审计和访问控制。
4. **容器 findings**：第三方镜像扫描结果会记录但不自动阻断；采用方必须阅读 evidence 并自行决定风险接受，不能据此声明零漏洞。
5. **可靠性边界**：spool、ACK 前持久化、重试和 dead-letter 是故障处理机制，不是零丢失证明；ClickHouse/事件迁移仍需观察 reconcile 和 backpressure。
6. **签名可复现性**：外置 Ed25519 trust root 和 digest pin 提升来源可核验性，但外部签名密钥、构建时间/环境、镜像来源和资产存储仍可能影响字节级复现，不宣称完整 reproducibility。
7. **数据迁移**：canonical event 的阶段门槛支持回滚和观测，但不能仅凭代码或本次 release 验证断言所有租户数据已完成迁移。

## 升级与采用建议

1. 先在目标 amd64 主机核对 Docker、磁盘、端口和包/主机架构，并核验包内镜像 pin 与外置 trust root；数据库镜像由离线包导入，不要求目标机预先缓存。不要把 trust root 放回离线包。
2. 在切换前保存当前 release 的配置、数据库备份和回滚路径，确认 runner 主机、Docker socket、缓存和 workspace 的权限边界。
3. 先验证 WebSocket 认证、Origin、角色、Agent credential、bootstrap loopback 和首次改密，再开放业务流量。
4. 观察 incident cutover、canonical event reconcile、transport spool/dead-letter、runtime health 和 rule reload/rollback；发现 degraded、backpressure 或 audit failure 时按 fail policy 处置。
5. 将 Java RASP 作为独立实验 profile，仅在受控 fixture/灰度环境验证；不要因其测试通过而纳入生产防护门槛。
6. 对容器扫描 `RECORDED` findings 建立人工评审和接受记录；发布成功只证明交付链路完成，不代表第三方镜像风险为零。

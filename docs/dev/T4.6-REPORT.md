# T4.6 查询性能与压测报告

## 环境

| 项 | 值 |
|---|---|
| 测试 VM | `lyflow-test` / `10.1.18.126` |
| CPU / RAM | 6 vCPU / 8 GiB |
| ClickHouse | 26.9.21.9，单节点，HTTP 8123 |
| ClickHouse 内存上限 | 4 GiB（profile `max_memory_usage` 3 GiB） |
| 数据集 | 30 天，5 EPS 采样，12,960,000 条 Event v2 |
| 压测工具 | `server/cmd/eventbench` + `server/bench` |

30 天 @ 20k EPS 理论约为 51.8B 行，单机测试 VM 无法容纳；本次用 5 EPS
采样保留 30 天时间分布，并单独验证 20k EPS 和 1Gbps 事件载荷的写入能力。
报告不把采样数据当作全量 20k EPS × 30 天数据。

## 结果

### 1. 30 天数据查询（索引后）

```text
dataset: 12,960,000 events / 30 days / 5 EPS
ingest: 19,650 EPS
queries: 10 组，20 次/组，0 errors
max p95: 728 ms
status: PASS
```

| detail_event | 61 ms |

### 2. 20k EPS 写入

```text
payload: 512B 估算
events: 1,200,000
writers: 1
measured: 21,525 EPS
status: PASS
```

### 3. 1Gbps 写入（5.5KB payload）

```text
payload: 5,500B
events: 600,000
writers: 8, batch: 10,000
measured: 22,114 EPS
approx payload throughput: 3.607 GB / 30s ≈ 1.06 Gbps
status: PASS
```

### 4. 30 天数据集 + 1Gbps 写入 + 查询

预加载 12.96M 30 天数据后，写入 600k 个 5.5KB 事件：

```text
throughput: 18,525 EPS
query max p95: 492 ms
query status: PASS
throughput status: FAIL (target 20,000 EPS)
```

同一测试 VM 上，单独写入 1Gbps 载荷达到 22.1k EPS；在已有 30 天索引表
上再写入时降到约 18.5k EPS。差异来自 part 数量、合并状态和内存/CPU 竞争。

### 5. 单次冷启动全流程

单次执行“30 天入库 + 1Gbps 入库 + 查询”时：

```text
retention ingest: ~82k EPS
throughput: ~18k EPS
optimize: 需要超过 60s；早期 60s HTTP 超时导致失败
query after failed optimize: p95 数秒，FAIL
```

已把压测客户端超时提高到 10 分钟，并增加 `OPTIMIZE TABLE ... FINAL`
阶段；但 6 vCPU / 8 GiB 单节点仍建议分离入库和查询压测，避免把后台
merge 时间和查询延迟混在一起。

## Schema 优化

新增数据跳过索引：

- `idx_event_uid`：`bloom_filter(0.01)`，修复 `detail_event` 从 34s 降到 50ms。
- `idx_asset_id`、`idx_user_id`、`idx_src_ip`、`idx_dst_ip`、
  `idx_process_exe`、`idx_file_hash`、`idx_rule_id`：`ngrambf_v1(3, 65536, 2, 0)`。

迁移版本 7 增加索引 DDL；已有表的索引 materialize 需要单独执行，不能
在在线低峰期之外自动做全表 materialize。

## 结论

- 30 天查询 p95 **< 2s**：通过（最大 728ms）。
- 20k EPS 正常事件写入：通过（21.5k EPS）。
- 1Gbps 事件载荷单独写入：通过（22.1k EPS，约 1.06Gbps）。
- 30 天索引表 + 1Gbps 同时写入：吞吐约 18.5k EPS，未稳定达到 20k。
- 当前 6 vCPU / 8 GiB 单节点可作为 lean 测试基线，但不能宣称
  “30 天 + 20k EPS + 1Gbps + 查询”在所有冷启动/合并状态下同时达标。

## 建议

1. 生产/正式验收使用 8+ vCPU、16+ GiB，ClickHouse 独立数据盘。
2. 入库与查询分离压测；查询前等待 merge/OPTIMIZE 完成。
3. 保留 batch=10k、writers=8 的调优参数作为起点，按节点规格调整。
4. 对 keyword 查询继续评估 projection 或专用搜索索引。
5. 1Gbps 是抓包链路指标；不要把 6KB 事件载荷直接等同于网络抓包事件率。

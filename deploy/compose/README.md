# LyFlow Compose profiles

Two deployment modes:

- **lean** (default): core services + ClickHouse/PostgreSQL/Redis/Web.
- **full-private**: lean + Elkeid HUB/Console/MongoDB/Kafka. This overlay is
  private and must not be published with public builds.

## Prerequisites

- Linux host with Docker Engine + Compose v2.
- Same architecture for all images.
- Core and sensor images can be built from the current tree/binaries:

```bash
cd /path/to/lyflow
# Build server, security-engine, Pingora frontend, Suricata and Redis.
bash deploy/compose/build-core-images.sh
# Build lyprobe, capturedoctor and rulecompiler from /opt/lyflow/artifacts.
LYFLOW_ARTIFACTS=/opt/lyflow/artifacts \
  bash deploy/compose/build-sensor-images.sh
```

`deploy/compose/pull-image.sh` tries several Docker Hub mirrors (including
毫秒镜像 `docker.1ms.run` and an optional `ALIYUN_MIRROR`) for base images that
the daemon cannot pull directly.

The frontend is a Pingora 0.9 service:

- `:80` returns a 308 redirect to HTTPS.
- `:443` serves `frontend/dist`.
- `/api/` and `/ws/` proxy to `ly-server:8080`.
- Injected `X-Forwarded-Proto` keeps install/API URLs HTTPS behind the proxy.

The test-only `g5-host.yml` uses host networking and a native ClickHouse because
public mirrors were unreliable during G5. See `docs/dev/G5-REPORT.md`; production
must use pinned digests or an offline image bundle.

## Lean quick start

```bash
cd deploy/compose
cp lean.env.example lean.env
# edit lean.env: passwords, management interface, capture interface,
# LYPROBE_TEMPLATE, image tags
./lyflowctl bootstrap
./lyflowctl config
./lyflowctl up
```

`bootstrap` creates `lean.env` with random secrets if missing, prepares
`runtime/fp-patterns`, `runtime/rules/source` and `runtime/status`, and seeds
the generated LyFlow sample rules. For real ET/CRS rules, put source files in
`runtime/rules/source`; the rule compiler watches them and updates
`runtime/fp-patterns/threat.json` atomically.

Open `https://<host>/` for the UI. First login is `admin`; the initial password
comes from `DEFAULT_ADMIN_PASSWORD` in `lean.env` and must be changed at first
login. Set a strong value there before exposing the host. Only Linux
server/agent deployment is supported; Windows/Npcap is not part of this stack.

## Capture profile

The capture services run with `network_mode: host` and require root/Docker
capabilities:

- `lyprobe-sensor`: `NET_RAW`, `NET_ADMIN`
- `suricata-sensor`: `NET_RAW`, `NET_ADMIN`, `SYS_NICE`
- `lyflow-capturedoctor`: `NET_ADMIN` + host PID namespace
- `lyflow-rulecompiler`: writes the shared `runtime/fp-patterns` directory

Set in `lean.env`:

```text
LYPROBE_INTERFACE=ens160
SURICATA_INTERFACE=ens160
LYPROBE_COLLECTOR=127.0.0.1:9995
LYPROBE_TEMPLATE=%PROTOCOL %IN_BYTES %IN_PKTS %IPV4_SRC_ADDR %IPV4_DST_ADDR %L4_SRC_PORT %L4_DST_PORT %THREAT_TYPE %THREAT_NAME %THREAT_VERS
```

The `%PROTOCOL` field is mandatory; without it ly_probe disables protocol
filtering and `"protocol":"tcp"`/`"udp"` threat rules cannot match.

The sensor images expect `/opt/lyflow/fp-patterns` to contain the upstream
`service.json`, `device.json`, `os.json`, `midware.json` plus the generated
`threat.json`. `bootstrap` copies them from `LYPROBE_SOURCE_DIR` when available.

## Server-zone capture profile (P2 traffic engine)

`server-zone-capture.yml` is an overlay for a sensor that sits in the server
zone (not at the internet edge). It only analyses external → server-zone
inbound and server-zone → external outbound (C2, tunnels, mining, exfiltration).
East-west traffic is out of scope.

```bash
docker compose -f lean.yml -f server-zone-capture.yml \
  --profile core --profile capture up -d
```

The profile adds/overrides four services:

- `lyprobe-sensor`: L7/fingerprint engine, reads the high-confidence subset.
- `lyflow-netflow-collector`: raw UDP NetFlow v9 listener on
  `${NETFLOW_BIND_ADDRESS:-127.0.0.1}:9995`, forwards to
  `/api/v1/agent/traffic-event`. Requires `NET_RAW` and the ingestion
  credentials.
- `lyflow-vector`: Suricata EVE alerts to `/api/v1/agent/component-alert`.
- `lyflow-rulecompiler`: compiles
  `/app/rules/compiled/server-zone/lyprobe-source.rules` into
  `runtime/fp-patterns/threat.json`.

The rule profile is generated by the platform, never pulled from the internet:

```bash
curl -X POST https://<host>/api/v1/traffic/rule-profile/export \
  -H "Authorization: Bearer <token>"
```

It writes `rules/compiled/server-zone/suricata.rules`,
`lyprobe-source.rules` and `profile-manifest.json`. `overlap_count` must be 0;
the export fails closed otherwise.

Current limitations:

- `suricata-sensor` remains defined in `lean.yml`; switch its rule mount to
  `../../rules/compiled/server-zone/suricata.rules` after the first export.
- The collector binary is copied into the lean server image
  (`/app/lyflow-netflow-collector`); the host build must produce
  `server/lyflow-netflow-collector` before building that image.
- The rule compiler does not restart `lyprobe`; lyprobe reloads `threat.json`
  through the patched build. Without the patch, set `LYFLOW_RULE_RELOAD` and
  run the compiler as a host service instead.

## Full-private overlay

```bash
LYFLOW_PROFILE=full-private ./lyflowctl config
LYFLOW_PROFILE=full-private ./lyflowctl up
```

Set `ELKEID_HUB_IMAGE`, `ELKEID_CONSOLE_IMAGE`, `ELKEID_AGENTCENTER_IMAGE`,
`ELKEID_MANAGER_IMAGE`, `ELKEID_SERVICE_DISCOVERY_IMAGE` and
`ELKEID_PRIVATE_DIR` in `lean.env`. The private overlay is not included by
`lean.yml`; do not copy `private/elkeid` into public artifacts.

## Upgrade, rollback and backup

```bash
./lyflowctl upgrade   # back up env, pull images, restart
./lyflowctl rollback  # restore latest env backup, restart
./lyflowctl backup    # PostgreSQL dump under deploy/compose/backups/
```

`upgrade`/`rollback` retain named volumes. Destructive volume removal requires
an explicit snapshot/confirmation and is intentionally not automated.

## Validation

```bash
./lyflowctl config
docker compose -f lean.yml --profile core --profile capture config
docker compose -f lean.yml -f full-private.yml \
  --profile core --profile capture --profile full-private \
  --env-file lean.env config
```

## Evidence profile

`seaweedfs` is available under the `evidence` profile. Start it with core:

```bash
EVIDENCE_OBJECT_STORE=filer \
EVIDENCE_FILER_URL=http://seaweedfs:18888 \
docker compose -f lean.yml --profile core --profile evidence up -d
```

It exposes the master (`19333`), volume (`18080`), filer (`18888`) and S3
(`18333`) ports on the internal network and stores data in `seaweed_data`.

Wazuh manager and the OpenRASP Java engine are native host services. See
`deploy/native/README.md`; they are intentionally not linked into the Go
binary or public image.

## Current limitations

- Core server/frontend image builds remain in the existing CI/build pipeline;
  this directory packages deployment and the new sensor images.
- Wazuh manager / OpenRASP / offline package digests still need to be pinned
  for a fully reproducible release. Vector and SeaweedFS are now in the
  deployment profiles.
- 6 vCPU / 8 GiB is a lean test baseline; T4.6 measured a combined 20k EPS +
  1Gbps ingest at ~18.5k EPS. Use 8+ vCPU / 16+ GiB for formal capacity
  acceptance.
- Windows endpoint support is intentionally removed; only Linux amd64/arm64
  are shipped.
